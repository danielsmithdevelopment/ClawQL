# ClawQL plugin model — horizontal packages and MCP tools

> ## ⚠️ 8.0.0 update — Phase-2 `onRegister` is historical
>
> The **Phase-2 `Plugin.onRegister` / `beforeCallTool`** interface described for most of this document was **removed in 8.0.0** ([#999](https://github.com/danielsmithdevelopment/ClawQL/issues/999)). There is **no compatibility bridge**. The current plugin model is **`ProviderPlugin`** / **`StandaloneSkillPlugin`** from `clawql-core`, which declare **`tools`** / **`hooks`** and are installed via `defineProviderPlugin` / `defineRegisteringProviderPlugin`; hooks fire through **`fireHook`**, not `beforeCallTool`.
>
> - **Migration guide:** [`docs/getting-started/migrate-to-8.0.md`](../getting-started/migrate-to-8.0.md)
> - **Current spec:** [`docs/design/clawql-core-plugin-architecture.md`](./clawql-core-plugin-architecture.md)
>
> Sections below that describe `onRegister` / `Plugin.beforeCallTool` are kept as a **historical record of the 7.x (Phase 2) design** — see [§2](#2-current-80-plugins-are-providerplugin) for the current model.

**Status:** Phase 2 (`onRegister`) shipped in 7.x and is now **historical**; as of **8.0.0**, plugins are **`ProviderPlugin`** / **`StandaloneSkillPlugin`**. HITL and third-party API remain roadmap  
**Audience:** Contributors, integrators, and third-party plugin authors  
**Related:** [Migrate to 8.0](../getting-started/migrate-to-8.0.md) · [clawql-core plugin architecture](./clawql-core-plugin-architecture.md) · [Modularization implementation status](./modularization-implementation-status.md) · [Effect + plugin plan](./effect-ts-modularization-rearchitecture-plan.md) · [Plugin registry](../reference/clawql-plugin-registry.md) · [Contributor Technical Specification §1.1](../contributing/clawql-contributor-technical-specification.md)

This document explains what it means for **`clawql-memory`**, **`clawql-documents`**, and **`clawql-automation`** to become **plugins**, how that differs from today’s layout, and how third-party plugins will work.

---

## 1. One-sentence summary

A **plugin** is how a package tells **`clawql-api`**: “When I’m enabled, register my MCP tools, wire my background workers, declare my provider dependencies, and participate in gateway hooks — and when I’m disabled, leave zero footprint.”

For memory, documents, and automation, **yes — the plugin’s main visible job is registering the respective MCP tools** (`memory_ingest`, `memory_recall`, `ingest_external_knowledge`, `schedule`, `notify`). Plugins also own **lifecycle** and optional **pipeline hooks**, not just tool names.

---

## 2. Current (8.0): plugins are `ProviderPlugin`

Extraction phases 1–9 moved **business logic** into workspace packages. As of **8.0.0**, MCP registration for horizontal packages is done by authoring a **`ProviderPlugin`** (`clawql-core`) that declares **`tools`** — directly, or generated by **`defineRegisteringProviderPlugin({ register })`** for env-gated sets — instead of implementing a `Plugin.onRegister` method.

| Package             | Logic lives in                                              | MCP registration                                                  |
| ------------------- | ----------------------------------------------------------- | ----------------------------------------------------------------- |
| `clawql-memory`     | `runMemoryIngest`, `runMemoryRecall`, vault, `memory.db`, … | ✅ **`MemoryPlugin`** (`ProviderPlugin`, `tools`)                 |
| `clawql-documents`  | `runIngestExternalKnowledge`, URL formatting                | ✅ **`DocumentsPlugin`** (`ProviderPlugin`, `clawql-documents/plugin`) |
| `clawql-automation` | schedule worker, `runNotifySlack`                           | ✅ **`AutomationPlugin`** (`ProviderPlugin`, `clawql-automation/plugin`) |

Transport-only concerns stay in `src/` today:

- Zod schemas at `server.tool(...)` registration time
- `wrapMcpToolHandler` (OpenTelemetry)
- `logMcpToolShape` (payload shape logging, no secrets)
- `CLAWQL_ENABLE_*` gates in `registerTools()`

**Remaining in `tools.ts`:** HITL and any tools not yet moved to a plugin package.

> **Historical (7.x, Phase 2):** Before 8.0.0, the same packages registered tools via a **`Plugin.onRegister`** method (`MemoryPlugin.onRegister`, `DocumentsPlugin.onRegister`, `AutomationPlugin.onRegister`). That interface — including `Plugin.beforeCallTool` for enforcement — is **removed** in 8.0.0 with no compatibility bridge. See [Migrate to 8.0](../getting-started/migrate-to-8.0.md).

## 3. Horizontal plugins (shipped)

At gateway startup, composition looks like:

```ts
createClawQLApi({
  plugins: [
    PanguardProxyPlugin, // ProviderPlugin, hooks only (opt-in, CLAWQL_PANGUARD_PROXY_PLUGIN=1) — policy chokepoint, no new tools
    MemoryPlugin, // memory_* + pageindex_* when enabled
    DocumentsPlugin, // ingest_external_knowledge when enabled
    AutomationPlugin, // schedule + notify; starts schedule worker
    // future: LendingPlugin, YourCompanyPlugin, …
  ],
});
```

When **`CLAWQL_ENABLE_MEMORY=0`** (or the Operator CRD omits the memory Layer), **`MemoryPlugin` is not composed** → `listTools` has no `memory_ingest` / `memory_recall`, and heavy vault/sql.js paths are not loaded for that process tier.

### 3.1 MCP tools each horizontal plugin registers

| Plugin               | MCP tools                                              | Notes                                                                                         |
| -------------------- | ------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| **MemoryPlugin**     | `memory_ingest`, `memory_recall`, `pageindex_*`        | PageIndex via `clawql-pageindex`; hide with `CLAWQL_ENABLE_PAGEINDEX=0`                       |
| **DocumentsPlugin**  | `ingest_external_knowledge`, optional Onyx / IDP tools | Bulk Markdown + URL ingest; IDP runner when enabled                                           |
| **AutomationPlugin** | `schedule`, `notify`, `workflow`, `argocd` (opt-in)    | Schedule worker starts on plugin registration; notify uses execute path for Slack `chat_postMessage` |

Core tools **`search`**, **`execute`**, **`cache`**, and **`audit`** stay in the gateway / core tier — not owned by these horizontal plugins.

### 3.2 `ProviderPlugin` contract (shipped, 8.0)

Horizontal plugins are **`ProviderPlugin`** values that declare **`tools`** (or use **`defineRegisteringProviderPlugin({ register })`** for env-gated tool sets). Illustration:

```typescript
import { defineRegisteringProviderPlugin } from "clawql-core";
import { Effect } from "effect";

const MemoryPlugin = defineRegisteringProviderPlugin({
  id: "clawql-memory",
  version: "1.0.0",
  description: "Vault memory tools",
  register: (api) =>
    Effect.gen(function* () {
      yield* api.registerMcpTool({ name: "memory_ingest", schema: memoryIngestSchema, handler: handleMemoryIngest });
      yield* api.registerMcpTool({ name: "memory_recall", schema: memoryRecallSchema, handler: handleMemoryRecall });
    }),
});
```

Handlers call into **`clawql-memory`** (`runMemoryIngest`, etc.). Transport wrappers (`logMcpToolShape`) may remain in a thin MCP adapter or move behind a small registration helper on `ClawQLApi` — that detail is implementation, not the model.

> **Historical (7.x, Phase 2):** the equivalent shipped as `Plugin.onRegister` calling `ClawQLPluginRegistrationApi.registerMcpTool(name, schema, handler)` with positional args. The interface name, method, and argument shape all changed in 8.0.0 — see [Migrate to 8.0](../getting-started/migrate-to-8.0.md) for the rewrite sketch.

## 4. Plugins are more than tool registration

Tool registration is what most integrators see. The full plugin contract (see [Contributor Technical Specification §1.1](../contributing/clawql-contributor-technical-specification.md)) also includes:

| Capability                                | Purpose                                    | Example                                                     |
| ------------------------------------------ | ------------------------------------------ | ------------------------------------------------------------ |
| **`tools`**                               | Register MCP tools                         | MemoryPlugin adds `memory_*` tools                          |
| **`hooks`** (blocking `tool` / `pre-execute`) | Run at a fixed lifecycle point, via `fireHook` | **Panguard** (opt-in) — no new tools                     |
| **`requiredSpecs` / `recommendedSpecs`**  | Startup validation                         | AutomationPlugin `notify` may require Slack in loaded spec  |
| **`onIngestHook`**                        | Transform/filter nodes entering Memory 2.0 | Vertical enriches or rejects ingest payloads                |
| **`onRecallFilter`**                      | Tighten recall beyond ATR                  | Ethical wall, patient partition                             |
| teardown / cleanup                        | Graceful shutdown                          | AutomationPlugin stops schedule worker, closes sql.js DB    |

> **Historical (7.x, Phase 2):** this table listed **`onRegister`** (tool registration) and **`beforeCallTool`** (`mcp-proxy` kind, run before any MCP tool) instead of `tools` and hooks-via-`fireHook`.

### 4.1 Panguard: plugin without tools

**`PanguardProxyPlugin`** is shipped and **opt-in** (`CLAWQL_PANGUARD_PROXY_PLUGIN=1` — not composed by default in 8.0.0). It does **not** register MCP tools. It declares blocking `hooks` (`tool` / `pre-execute` scope) so policy/ATR runs on every tool invocation when enabled, fired via `fireHook`. Same `ProviderPlugin` interface, different role — shows that “plugin” ≠ “adds tools” only.

> **Historical (7.x, Phase 2):** Panguard implemented **`beforeCallTool`** directly and was composed by default; both of those are no longer accurate in 8.0.0.

## 5. Shipped vs target (honest matrix)

| Item                                       | Shipped today (8.0.0)                                                                     | Target                                                                                         |
| ------------------------------------------ | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| `ProviderPlugin` interface                 | `id`, `version`, `description`, `tools`, `hooks`, `requiredSpecs` in `clawql-core` (Phase-2 `Plugin.onRegister` / `beforeCallTool` removed, #999) | Full contract in contributor spec (`onIngestHook`, richer `requiredSpecs`, …)                  |
| `PluginRegistry` + `createClawQLApi()`     | ✅                                                                                       | ✅                                                                                             |
| Memory / documents / automation as plugins | ✅ **MemoryPlugin**, **DocumentsPlugin**, **AutomationPlugin** as `ProviderPlugin`         | Effect `Layer` wrappers; Argo `workflow` on AutomationPlugin ([design](workflow-tool-argo.md)) |
| Third-party npm plugins                    | ❌ No public registration API                                                            | Publish `clawql-*-plugin`; compose via Operator / env                                          |
| Effect `Layer` per horizontal package      | ❌ Domain code mostly `async`                                                            | `MemoryLayer`, `DocumentsLayer`, `AutomationLayer` composed at bootstrap                       |

## 6. What extraction already did vs what “becoming plugins” finishes

| Done (package extraction)                                                       | Remaining (plugin work)                                                                                                                                              |
| ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `runMemoryIngest`, `runMemoryRecall`, vault, `memory.db` in `clawql-memory`     | ✅ `MemoryPlugin` (`ProviderPlugin`) declares `memory_*` tools; `tools.ts` calls `registerPluginMcpTools()`                                                          |
| `runIngestExternalKnowledge` in `clawql-documents`                              | ✅ `DocumentsPlugin` (`ProviderPlugin`) declares ingest + optional Onyx tools                                                                                        |
| Schedule + notify in `clawql-automation`; `configureNotifyDeps` from `tools.ts` | ✅ `AutomationPlugin` (`ProviderPlugin`); `configureAutomationPluginDeps` wires execute. **Designed:** Argo `workflow` tool ([workflow-tool-argo.md](workflow-tool-argo.md)) |
| Thin MCP shims + `logMcpToolShape` in `src/`                                    | Keep transport-only concerns in MCP package or `registerMcpTool` helper                                                                                              |

**Becoming plugins does not mean moving more files** — it means **owning MCP surface area and lifecycle when enabled**, instead of centralizing registration in `tools.ts`.

## 7. Third-party and vertical plugins

The same model extends to **verticals** (`clawql-lending`, `clawql-legal`, …) and **community extensions**:

1. Publish an npm package (e.g. `clawql-acme-widgets`) depending on **`clawql-core`** + **`clawql-api`** — **not** on `clawql-mcp` transport internals.
2. Export a **`ProviderPlugin`** (Effect `Layer` under the hood) via `defineProviderPlugin` / `defineRegisteringProviderPlugin`.
3. Declare **`tools`** for your MCP tools and **`requiredSpecs`** if you need Postgres, Onyx, etc.
4. Document the Operator toggle or `CLAWQL_ENABLE_*` flag that includes or omits your Layer.

Until Layer composition is stable, in-repo extensions should continue via **bundled providers** (`providers/`) and MCP tools in the monorepo. Third-party registration without forking `tools.ts` is explicitly **roadmap**, not current API.

---

## 8. Request flow (target)

```
Agent (stdio / HTTP / gRPC)
        │
        ▼
  MCP transport (src/server*.ts, thin tools adapter)
        │
        ▼
  createClawQLApi({ plugins: [...] })
        │
        ├── Core: search / execute / cache / audit (always on)
        │
        ├── PanguardProxyPlugin hooks via fireHook (every tool, opt-in — CLAWQL_PANGUARD_PROXY_PLUGIN=1)
        │
        └── If MemoryPlugin composed:
              memory_ingest / memory_recall → clawql-memory
            If DocumentsPlugin composed:
              ingest_external_knowledge → clawql-documents
            If AutomationPlugin composed:
              schedule / notify → clawql-automation
```
