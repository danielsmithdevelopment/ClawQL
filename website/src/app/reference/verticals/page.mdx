# Verticals guide

Domain verticals are **plugin presets** for an industry — not a separate product line. Enabling **lending**, **legal**, or **healthcare** composes the horizontal plugins that domain needs (almost always [Memory](/plugins/memory), usually [Documents](/plugins/documents)) and ships **domain-tailored boilerplate** such as ready-to-use or ready-to-modify [`.cqw` workflows](/specs/cq-extensions/cqw). {{ className: 'lead' }}

## Mental model

| Layer                  | What it is                                                     | Example                                                                        |
| ---------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| **Horizontal plugins** | Reusable capabilities                                          | Memory, Documents, Automation, Sandbox                                         |
| **Domain vertical**    | Preset / bundle that **composes** horizontals + domain surface | Lending pulls Memory + Documents, then adds LOS tools and lending `.cqw` files |
| **Boilerplate**        | Differentiated per vertical                                    | Underwriting vs privilege-review vs claims `.cqw` starters                     |

Verticals do **not** reimplement Memory or Documents. They declare those plugins as part of the install shape (Operator / Effect Layers / `requiredSpecs`) and focus differentiation on domain tools, compliance hooks, and workflow templates.

## Verticals are still plugins

| Concern             | Same as horizontal plugins? | Notes                                                                              |
| ------------------- | --------------------------- | ---------------------------------------------------------------------------------- |
| Registration        | Yes                         | `Plugin.onRegister` / Effect Layers when composed                                  |
| Opt-in footprint    | Yes                         | Disabled verticals have **zero runtime footprint**                                 |
| Cross-package calls | Via gateway                 | Verticals **never import other verticals** — use **`clawql-api.execute()`**        |
| Enable path         | Operator / CRD              | Planned **`ClawQLInstance`** flags (not shipped) instead of only `CLAWQL_ENABLE_*` |

Browse the full catalog on [Plugins](/plugins) — kind **Domain vertical**, with **Composes** and **Boilerplate** on each row.

## Design rules

- Verticals **never import other verticals** — cross-domain operations route through **`clawql-api.execute()`**
- Disabled verticals have **zero runtime footprint** (Operator / `ClawQLInstance` CRD)
- Each vertical declares **`maxClassificationLevel`**, required ATR purposes, and Presidio policies
- Domain **`.cqw`** (and related `.cq*`) starters should be tailored to that vertical’s workflows — not generic copies of another domain’s pack

## Enabling a vertical

1. Set vertical flags in planned **`ClawQLInstance`** spec — see [Operator target architecture](/design/operator-target-architecture) §6 (not shipped)
2. Register vertical plugins at gateway startup; composed horizontal Layers (Memory, Documents, …) come with the preset
3. Run vertical-specific evaluation suites before production promotion
